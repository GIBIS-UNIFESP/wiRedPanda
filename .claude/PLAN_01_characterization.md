# Plan 1: characterization on `master`

Goldens of `master`'s behaviour, each generated by running its test on `master` itself, and the tools the later plans
measure with. Every later plan names each golden it changes, with the cause, so a structural change that silently
alters a picture, a hit result, a trace or a file's bytes fails a golden instead of reaching users. Plan 1 changes the
application in one place, which the fixture generator needs: the status bar's element count comes from a count the
item registry keeps, instead of a sort of the circuit. Before its goldens, it also fixes the `master` defects that
failed its CI (§4.6).

- **Depends on:** nothing. It is the first plan to land, after the branch that holds the plan files.
- **Lands before:** every other plan. The plans run one at a time, in their order (the plans' rules, §1), so plan 2
  starts once plan 1 has landed, its fixes on all of plan 1's goldens.
- **Branch and ledger:** `01-characterization`, from `00-plans`, in slices (the plans' rules, §1 and §3).
  `LEDGER_01_characterization.md` has a row for every step, open question and unchecked claim below.
- **Rules every plan shares** (slices, each commit correct from its first line, validation on the relwithdebinfo
  preset, ASan, UBSan and clang left to CI, the rules for new tests) are the plans' rules (`PLAN_rules.md`), and how
  tests are built, registered and run is `CLAUDE.md`'s "Building and testing"; this file states plan 1's own. Its
  decisions are numbered P1.D1 on.

## 1. Two rules the branch taught

- **Generated on the unchanged base.** On `gpu-canvas`, goldens added after later changes had landed were generated
  with those changes in place, so they pinned the changed behaviour, and a gate had to regenerate them on the base and
  compare. Plan 1 runs on `master`'s code before any other plan changes it, so every golden is `master`'s.
- **Every check shown to fail.** Each golden and check is broken on purpose once (an order reversed, a render skipped,
  a type removed from a list, a fixed defect put back) and must fail, then pass on the code. On the branch several
  goldens passed while pinning nothing; each case is under its golden below. The break is made locally and not
  committed; the commit message says what was broken and that the test failed.

## 2. How the goldens work

- One helper compares a text dump with its golden file, and another compares bytes. With `GENERATE_EXPECTED_SNAPSHOTS`
  set, both write the golden instead, also when a golden already exists; on the branch the byte helper first ignored
  the switch when a golden existed, so a regeneration left old bytes in place.
- The variable counts as set even when it is empty (`GENERATE_EXPECTED_SNAPSHOTS=` regenerates every golden), so
  nothing that runs the suite may export it.
- A missing golden fails rather than being written; a missing input directory adds a row that fails, naming the
  directory.
- Shared helpers list the elements sorted by id, and print numbers (negative zero as zero), points, quoted strings,
  statuses and the sixteen orientations (four rotations, each unflipped, flipped horizontally, vertically and both
  ways) the same way in every dump.
- Element internals are read through a test-only friend class, not a production accessor.
- A type without a creator is written as `NO CREATOR` and fails its golden; the types left out on purpose are named in
  one list (IC, whose bare element has no file, so ICs are dumped through the circuits that hold them; JKLatch and
  Unknown, which have no creator), where a silent skip had hidden types on the branch.
- Comments say what a golden pins and how, and claim no coverage a test lacks (one on the branch said paste was pinned
  where it was not), with no ledger rows, defect IDs or history.
- The tests compile under the flags CI's Apple clang build uses: no `QWARN`, and no `float` passed where a `qreal` is
  expected (`-Wdouble-promotion`); nothing checks clang locally.
- `master`'s CI builds Qt 6.8.3 and 6.9.3 on x86-64 and ARM64, and Debian's 6.8.2 on i386, so these goldens run on
  the 6.8 floor that the Qt floor's plan, right after plan 2, declares; no CI job runs an older Qt.
- Each new test class is registered in the four places `CLAUDE.md`'s "Building and testing" names, and carries CTest
  labels that match what it does.

## 3. The goldens

### 3.1 Scene snapshot

Every circuit in `Examples`, the IC components, `Tests/Fixtures` and the perf fixtures is loaded and dumped: elements by
id, each port with its position in the element and in the scene, and the wires reached through their ports, never
through the scene's items. Of a port's and a wire's `QGraphicsItem` API the dumps read only a port's `pos()` and
`scenePos()` and, for §3.2, a wire's `path()`; when plan 9 takes ports and wires out of the item tree it keeps
accessors with those meanings, so the goldens hold (§9). The picture each element shows is recorded by size, source
and whether an oriented variant replaces the base picture, not by pixels (P1.D2). A second test fails on a golden whose
circuit is gone.

### 3.2 Wire geometry after an edit

The snapshot also edits each top-level fixture once by each of a move, a rotation, a flip and a port-count change, and
dumps the wires' ends with every point of their paths, and the edited element with its ports. Three traps made the
branch's first version pin nothing:

- the suite runs with `Application::renderingEnabled` off, so `Connection::updatePath()` returns before building a path,
  and a wire's ends were read from its ports' live positions; the test holds rendering on, from before the load, with
  a scoped switch;
- the port-count edit picked an InputSwitch in every fixture, whose port count cannot change, so it changed nothing; a
  separate resize edit acts on an element with a variable input count;
- the rotation and flip edits picked the same InputSwitch, which does not rotate its graphic (its port is re-routed
  instead), so further rows act on elements whose graphic rotates: an IC, an And and a Not.

### 3.3 Port layout

Every type at every legal port count, not a sample (the largest range is `InputRotary`'s 2 to 16 outputs; Mux inputs
as the element editor offers them; Demux inputs derived from its outputs), and the full-adder IC, in all sixteen
orientations printed in full rather than hashed, so a failure names the port: each port's name, position, required flag
and default status. Port names are taken under a tagging translator; on `master` they are literals except the segment
displays', whose descriptions go through `tr()` (`"G (" + tr("middle") + ")"`), so the golden pins those tagged and
every other name untagged, and a name that later starts or stops going through `tr()` shows there. A second pass
orients first and then changes the count (or loads the IC, as a reload does) and prints only where the result differs
from changing the count first. On `master` it shows an IC turning about a different centre before its load than
after, which plan 2 checks on a flipped IC reopened from a file (on the branch it landed 64 px off).

### 3.4 Hit testing and pointer behaviour

A grid over every small fixture at a step of 4, a quarter unit off the grid lines so no sample sits on an edge, records
per point the topmost element or wire whose shape holds it (what a plain click lands on), `Scene::portAt()` and
`itemAt()`, each by element id rather than item identity. The grid's area comes from element bodies and port positions,
not `itemsBoundingRect()`, which changes when ports and wires stop being items. A wire in the Error status is sampled at
a step of 0.5 around its middle, straddling the half-widths 1.5 and 2.5: its pen, and so its click width, is 5 wide
against 3.

Real `QGraphicsSceneMouseEvent`s, sent under a workspace (Ctrl's clone-drag needs a view), pin: wire selection;
Ctrl-click and Shift-click (a toggle); an empty click; a press and release without movement on an element of a
multi-selection; a multi-element drag; the rubber band; starting a wire and detaching one; a selected wire cleared by a
press on an element or an empty click; a wire selected alone through delete, cut, copy, duplicate, the context menu,
select all and zoom to selection; the selection a duplicate leaves; and the grid again with gates hidden and with wires
hidden. Each gesture is its own test function: a click selecting a wire alone, Ctrl-click adding without toggling,
Shift-click toggling, an empty click clearing, a drag of a selection and of an unselected element, the rubber band, a
drag from an output to an input, a click on an output routing until a press on an input, a drag from a free input to an
output. `TestMainWindowGui` already drives some of the same gestures through the main window; they stay as they are.

The input switch is never pressed, since a press toggles it. The clone-drag gesture starts a `QDrag`
(`ClipboardManager::cloneDrag()`) whose `exec()` a test cannot drive, so its drop is pinned by sending enter, move and
drop events to the scene. Paste goes through the system clipboard, so every test that copies, cuts or pastes holds
CTest's `clipboard` resource lock.

This golden pins two `master` defects as they are, for plan 2: `portAt()` returns the port drawn below another, since
Qt's `items()` lists in ascending stacking order, and `itemAt()` does the same. With overlapping elements a press goes
through Qt to the top one while the scene's lookup answers the bottom one, so a drag of the top element snapshots the
bottom one and pushes no move command: the move cannot be undone.

### 3.5 Simulation traces

Every logic type at its fewest and its most ports (Mux with 3 and 11 inputs, Demux by its outputs, the truth table at
2×1 and 8×8 with a seeded key), through every input combination up to eleven wired inputs (so only the 14- and
16-segment displays are walked alone, by a seeded walk), wired and with the last input open; the six small fixtures,
all 73 IC components, the four-gate perf IC and the IC-heavy circuit (24 steps of its one switch).

- Clocks are frozen by never starting the simulation timer, which the test asserts, since `update()` advances clocks
  only while the timer runs and `initialize()` sets them HIGH; a throttle disabler keeps each step complete whatever the
  interactive mode says.
- Seeds are FNV-1a of the run's name, not `qHash`, which is seeded per process and differs between Qt builds, and two
  random draws in one call are sequenced explicitly, since argument evaluation order is the compiler's.
- The untraced types are listed (IC, Clock, AudioBox, Buzzer, Text, Line), and a type without a creator fails rather
  than being skipped.
- An element that drives nothing is traced through its input ports' statuses, which is what the displays and the LED
  paint from: the branch first traced it through its simulation inputs, and since the 7-, 14- and 16-segment displays
  have no logic of their own, nothing refreshed those, and their traces were all zeros whatever the switches did.

Plan 5 names every difference from these traces by its cause.

### 3.6 Labels

Each label's scene transform for every labelled type and orientation: fourteen types show a label (six of them rotate
their graphic), plus the IC. Label anchors are fixed points, never text widths, so the transform is font-free; the
truth table's and the IC's anchors follow their bodies, so those run at their fewest and most ports, with each
orientation applied both before and after the count. The 17 label-less types are listed as such, not skipped.

### 3.7 Wire pixels

`master` has no wire layer, so the test paints each visible wire with its scene transform in Qt's stacking order, for a
synthetic circuit and the 2,000-element clocked fixture, at several scales and window positions. It cannot use
`scene->render()`, since `Scene::drawBackground` adds the grid dots. Adaptive antialiasing is degraded only on the
passes `GraphicsView::paintEvent` measures, so painting outside a view keeps it on, which the test asserts. Coverage is
portable fixed-point but solid blending has per-SIMD variants, so each channel may differ by 2 and no pixel by more;
that bound was never checked off the development machine, and it widens only on CI evidence (§8). Tests start on the
System theme, so the test pins Light.

### 3.8 Stacking

A render of three overlapping elements with their ports and labels is not a stacking check on its own: the bodies do not
paint opaque overlaps, so on the branch some reorders changed no pixel while others did (changing one element's z
changed 1,007). Z-order goldens name every item (elements, ports, labels, wires, wireless indicators, the selection
rectangle) of all 27 example and fixture circuits, and one more pins the order after undoing the delete, and the morph,
of the bottom of three overlapping elements (on `master` the undo puts the restored element on top), and after the morph
itself, before its undo, where the morphed element is re-added with its id too (plan 2's P2.43 changes these rows).
The render itself is compared with Qt's own render of the scene, grid dots excluded. The branch never pinned the rubber
band or a wire being routed across overlapping elements, which need a view and the pending-wire state; plan 1 adds
them.

### 3.9 Snapping and the view

Align (six edges and centres), distribute, rotate, flip, move and nudge, each with its undo and redo; drag, drop and
paste through the real gestures. Every other site that decides a position has a row too: duplicate, the clone drop
(Ctrl-drag, sent as events), the add without a drag, the split's node, and the MCP's `create_element`, `move_element`
and `instantiate_ic` (through their handlers, as `TestElementHandler` drives them), each from an off-grid start where
one exists, since an element placed before it joins the scene keeps an off-grid position and an undo then comes back
snapped (plan 2's P2.42). The zoom ladder in both directions, zoom to fit, `centerOn`, `ensureVisible`, the wheel
zoom's recentring, and the scroll position, with its rounding, in every row.

The wheel zoom is a `master` defect the golden pins as it is, for plan 2. In `GraphicsView::wheelEvent`, `zoomIn()`
calls `scale()`, which pivots about the view's centre (`AnchorUnderMouse` applies only to Qt's own wheel handler, which
`wheelEvent` replaces), and `centerOn()` then puts the post-zoom point under the cursor at the viewport's centre instead
of under the cursor. Measured: the scene point under the cursor moved from (-192, -142) to (-307.2, -227.2), where the
centre that keeps it is (32, 26); the scroll clamp at the scene rect makes the error larger near the edges. Keyboard
zoom pivots on the centre and is not part of the defect.

### 3.10 IC previews

Every component's port counts and whether its preview has ink (73 rows; two components have no preview, null at 0×0),
each component's pins in order (the inner element's id, its port index and its label), which plan 2's regeneration of the
components on the grid and plan 4's saved pin order must leave unchanged,
and one preview's pixels: `level2_mux_8to1`, one of the three components whose labels stay inside the preview's
bounds, with wires drawn and labels masked, within the pixel tolerance. Three traps:

- preview sizes follow the label font in 70 of 73 components (mapping "Sans Serif" to DejaVu Sans failed 65 rows, to
  Liberation Sans 48), so no size is pinned;
- with rendering off, each wire's empty path adds a 20×20 rectangle at the scene origin to the bounds, so previews are
  taken with rendering on;
- an ink check that looks for alpha above 0 always passes, since the renderer fills the preview opaque, so it looks for
  a pixel other than the background.

The label masks are checked to cover every label, and the pixel golden fails when the preview stops drawing its labels.
Checking each preview's size against its circuit's bounds was rejected: it doubled the test's CPU time with a second
load per row, and the test was already the suite's longest.

### 3.11 Property editor and MCP

The property kinds each of the 31 creatable types offers the editor; what the editor writes for each kind, through its
own widget or dialog (the value written, the element's value before and after, and the undo commands pushed; 59 rows;
the truth table's own dialog is not driven); and MCP's responses: 13 calls of 11 element commands to each type alone in
a new tab, each result or error recorded (403 rows; a Text element's width and height masked, since they follow the
font; `morph_element` and `update_element` left out, since they echo their parameters). Both pass under Noto, DejaVu and
Liberation Sans. The editor golden pins three `master` defects as they are, for plan 2: the AudioBox's audio file is not
undoable, a lowercase trigger key pushes two undo commands, and Mux, Demux and the truth table offer a custom appearance
they never draw.

### 3.12 Generated code under a non-English interface

The Arduino and SystemVerilog generators run an And gate and each segment display (the 16-segment sketch needs an
Arduino Mega: 19 pins) under a translator that tags every string, and the output is compared with the English output.
The tag must contain letters (`[tr %1]`): the generators keep only letters, digits and `_` in identifiers, so a tag of
`[%1]` vanished (`G ([middle])` became `g_middle`, as in English) and hid any translated name leaking into an
identifier. On `master` the output under the translator differs from English only by the tag, in element type names
and segment names; the golden pins that, and plan 2's fix makes the two outputs equal. The display port names under
the translator are checked in both generators.

### 3.13 Translatable strings

A CMake target with `update_translations`' options (including `-tr-function-alias tr+=PANDACEPTION`),
`NO_GLOBAL_TARGET`, defined inside `Qt6LinguistTools_FOUND` and, as `master` sets those options, only on Qt 6.7 or later
(`master`'s minimum is 6.2 until the Qt floor), extracts the (context, source) pairs (618 on the branch) to
`build/translatable_strings.ts`, and a test compares them with a golden. Nothing but building that target refreshes the
extraction: it is outside `all`, and as a build dependency it would run on every build, having no outputs. So the test
skips until the target exists, and every check before a slice is finished, and CI, builds it before the suite. CI
builds it on one job (Linux x86-64, Qt 6.9.3, the Qt the translation workflow refreshes catalogs with); extraction
does not depend on the platform. A change that adds or removes strings builds the target and updates the golden in the
same commit.

### 3.14 File format

The uncompressed payload `master` saves after loading each example, fixture, IC component, perf fixture and
backward-compatibility file, with the header checked apart, since compressed bytes depend on the zlib Qt was built with.
The payload golden is where a serialization change shows first: on the branch, the 83 rows of the fixtures, components
and perf fixtures all changed with a fix that made the file header name an IC's pins as the loaded IC does, and 54
changed back with the next fix, which keeps the names the sub-circuit gives the pins across a reload (plan 4).

## 4. The tools

### 4.1 The element count, kept by the item registry

The generator needs one production change first. The status bar's element count calls `Scene::elements()`, a
topological sort, on every change and selection change (`SceneUiBinder`), so each MCP command costs about 0.011 ms per
element present: 2 ms at 500 elements, 65 ms at 6,000, about half an hour to generate the 8,000-element clocked circuit
and hours for the 20,000-element combinational one. With the count stubbed a command costs a flat 0.7 ms, and 6,000
elements take 7 s instead of 292 s. The count is kept by the item registry, which sees insertion, removal and
destruction (an item's kind is passed when it is registered, since an item being destroyed can no longer report it). On
the branch, forgetting an item's id once removed a live element from the count, so a test compares the count with a full
walk after every mutation path (add, remove, delete, undo, redo, destruction, load, id forgetting, copy, cut, paste,
duplicate, rotate, loading a file) in every build, and a debug assertion checks it on every walk.

### 4.2 The perf fixtures, from one generator

An MCP-driven, deterministic generator with the size as a parameter writes the clocked circuit (rows of 18 D flip-flops
behind one clock), the combinational one (rows of 18 And, Or and Xor gates, each fed twice) and the IC-heavy one (50
columns of a file-backed four-gate IC under one clock and one switch, the IC found relative to the fixture), every
position on the 8-pixel grid MCP snaps to. It exits with status 1 and a message on any failure, and writes the same
bytes from an unoptimized and an optimized build (the binary is chosen by `WIREDPANDA_EXE`; on the branch, the debug and
the release builds wrote byte-identical files); before its slice is finished it is run against the debug and the
relwithdebinfo builds, the preset every check uses, and the files compared. The small sizes (clocked 2,000,
combinational 1,000, IC-heavy 2,000) are committed in a linted directory; the large ones (clocked 8,000, combinational
20,000) are written outside the repository, in the format `master` writes. The profiling directory beside the
repository also holds files the branch wrote in its newer format, which `master` does not load
(`combinational_20000.panda`, `ic_heavy_rev102.panda`), while `combinational_10000.panda` and
`combinational_20000.v5.1.panda` load through the old-format path; the generator rewrites the ones plan 1 needs.

### 4.3 The probe harness

A harness counts instructions under callgrind for a load, a load followed by frames, an idle tick, adding a wire, an
undo, a move, a delete, frames and a pan, plus a count of wire extents outside valgrind. A script runs it; the test runs
only when `WIREDPANDA_PERF_PROBE` is set, which only the script sets (in the default suite it took 16 to 22 s, the
slowest test; with the variable set its 12 checks pass in about 20 s). What the branch learned making its numbers mean
something:

- rendering is on from before the load, since the suite's default leaves wires without paths;
- frames go through the workspace's own view, since the scene reads its view for the grid's zoom and the scene rect;
  the view is shown off screen (`WA_DontShowOnScreen`) and resized to 1280×800, because grabbing a hidden child
  activates the top-level layout, which overrides the view's size;
- fast mode is off, as in the application, and wire antialiasing is held on before each frame: under callgrind every
  pass exceeds the 50 ms budget after which the view turns it off;
- fitted frames use `zoomToFit()`; edits go through the scene's command path and the delete action, as the
  application's do; the load reads a stream, since loading by file name migrates an older file on disk;
- elements are picked in ascending id, never through `elements()`, whose topological order changes with the engine;
- each phase is a `Q_NEVER_INLINE` function (MSVC on CI inlines otherwise), and the script collects `*::phaseX(*`, so
  `phaseLoad` does not match `phaseLoadThenFrames`;
- CTest presets of schema version 3 ignore `filter`.

The environment variable's name is the same in the test, the script and the tests' README.

### 4.4 Test readers that tell a non-level from 0

On `master`, `inputStatus()` and `outputStatus()` in `Tests/Common/TestUtils` return a `bool`, whether the port is
Active, and `readMultiBitOutput()` sets a bit only for Active, so a test expecting 0 passes on Unknown or Error. They
return the port's `Status` instead, and the multi-bit reader a value that carries each bit's status, equal to a number
only when every bit is a level and printed as bits (`01U1`) when a comparison fails (P1.D5). On `master`, 99 test files
call them: about 590 lines with `inputStatus`, 5 with `outputStatus` and 90 with `readMultiBitOutput`. A test whose
expectation changes is named with the cause: `master` outputs a non-level where the test expected 0 (a defect for plan
2, or a reading plan 5 changes), or the test was wrong.

### 4.5 Two fast-path tests that could not fail

Two tests of the update command's fast paths (a clock's phase kept, the non-wireless node fast path) never call the
simulation's `update()` after the command, where the first update after a structural edit rebuilds the simulation and
sets every clock HIGH; so neither could fail. Each builds the simulation first and updates after the command, and each
is shown to fail with its fast path removed.

### 4.6 Fixes to `master` made on this branch

Three defects of `master` failed this branch's CI, so each was fixed here by a commit of its own placed before the
goldens, which therefore show none of them (P1.D7):

- **CI's MCP Integration Test (P1.30).** `install-qt-action` v4.4.1 puts its own Python, 3.14 or later, first on the
  `PATH` after `build.yml` installed the MCP client's requirements into 3.12, so every Linux and macOS job failed
  with `No module named 'beartype'`. The Python tooling moves to 3.14 and the action sets up none.
- **The IC file watcher test on Windows (P1.31).** The test rewrites the watched file at once, and Qt's Windows watcher
  compares owner, group, permissions and the last-modified time, never the size, so a rewrite within one timestamp
  tick is no change; `windows-11-arm` failed it in 2 of 4 runs. The rewrite gets a later modification time.
- **The editor's volume (P1.32).** The element editor set its volume slider to the volume times 100 truncated, and on
  32-bit x86, whose x87 unit keeps the product in extended precision, the buzzer's default 0.35 showed as 34, failing
  the editor-writes golden on CI's `debian-i386` job; in float arithmetic 0.53 and 0.59 do the same on every
  platform. The slider takes the product rounded, and a test reads back every percent from 0 to 100.

## 6. Decisions

Each ends with its basis: measured or tested (a run backs it), read (the code, with nothing run), or a ruling (the
user's choice between workable options).

- **P1.D1. Goldens of `master`, each shown to fail.** Every golden is generated on `master`'s code before any other
  plan changes it, and every check is broken on purpose once and must fail. Basis: the user's ruling of 2026-10-04
  that the characterization tests and tools of the `perf/load-hotspots` prototype are recreated on `master` first, by
  intent; the branch's evidence (§1).
- **P1.D2. Pictures recorded by what they are, not by pixels.** The scene snapshot records each picture by size,
  source and oriented variant. CI tests x86-64, ARM64 and i386 with Qt 6.8.3, 6.9.3 and the distributions' Qt; the
  twelve memory-element pictures draw Noto Sans text that FreeType, Core Text and DirectWrite rasterize differently; and
  solid blending has per-SIMD variants. Pixels are compared only in the few pixel goldens, with a per-channel bound and
  masks. Basis: read (CI's matrix on `master`; the pictures' text and Qt's blending, as the branch found them).
- **P1.D3. The perf fixtures come from one generator** (§4.2): the small sizes committed, the large ones written
  outside the repository in the format `master` writes. Basis: tested on the branch (byte-identical files from the
  debug and the release builds); the user's ruling of 2026-10-04.
- **P1.D4. The registry keeps the element count.** The one production change of plan 1 (§4.1), since without it the
  generator takes hours. Basis: measured on the branch (7 s against 292 s for 6,000 elements).
- **P1.D5. The test readers return what a port holds** (§4.4). They have to exist before any change can turn a 0 into
  Unknown. Basis: read on `master` (99 test files call the readers); the user's rulings of 2026-10-20 (the readers) and
  2026-10-21 (in plan 1).
- **P1.D6. `master`'s defects are pinned as they are.** A golden that shows a defect pins `master`'s behaviour, and
  plan 2's fix changes the golden, naming the cause: the hit test's answer of the bottom item, the wheel zoom, the
  AudioBox's audio file, the lowercase trigger key, the appearance Mux, Demux and the truth table offer but never draw,
  and translated names in generated code. Basis: the user's rulings of 2026-10-21 that every defect verified on

## 8. Claims to check and open questions

- **The wire-pixel bound on CI's renderers.** Each channel within 2 and no pixel more was measured on the development

  bound, with the CI evidence named (P1.21).
- **Gestures under the offscreen platform.** Whether `QDrag::exec()`, the clipboard and the zoom-to-selection bounds
  behave under the offscreen platform as on a desktop, and the hit grid's run time, were left open on the branch. Plan 1
  closes or records each (P1.22).
- **The first paint of the large circuit.** In July 2026 a profile of the `master` of the time found the first paint of
  the 8,000-element circuit still inside Qt's BSP index rebuild (`QGraphicsSceneBspTree`) at full CPU 90 seconds after
  launch; whether today's `master` still pays that was not measured. The probe times the load and its first frames, and
  the result is recorded (P1.23).
